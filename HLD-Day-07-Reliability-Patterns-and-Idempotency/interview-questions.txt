# Day 7 – Interview Questions (Reliability & Idempotency)

## Conceptual

1. Why are retries dangerous in distributed systems?
-> Retries can make outages worse because when a downstream system is already slow or unhealthy, retrying requests increases the 
load on it. This can lead to retry storms, exhaust threads and resources, and prevent the system from recovering, causing cascading failures.

2. Why are timeouts alone not sufficient?
-> Timeouts only limit how long we wait for a response, but they still allow requests to be sent continuously. Circuit breakers actively 
stop requests when a downstream service is unhealthy, preventing resource exhaustion and cascading failures.

3. Explain circuit breaker states.
-> There are 3 circuit breaker states:
    a. Closed (Normal): 
        - Requests go through
        - Failures are counted
    b. OPEN (Protection Mode):
        - Too many failures detected
        - Calls are blocked immediately
        - Fail fast instead of waiting
    c. HALF-OPEN (Test Mode):
        - After a wait, allow a few test calls
        - If success → close again
        - If failure → open again

4. What does fail-fast mean and why is it important?
->  It is better to fail fast because it prevents resource exhaustion and avoids cascading failures when a downstream system is unhealthy. 
   Instead of letting requests pile up and degrade the entire system, we reject them early, allowing the application to recover faster.

    This also limits the number of affected requests, making them easier to track. Depending on business requirements, rejected requests 
   can either be dropped, retried asynchronously using a queue, or served with cached, user-friendly fallback responses. The exact strategy 
   depends on whether the operations are idempotent and whether the business allows replaying failed requests.

## Idempotency

5. What is idempotency?
-> An operation is idempotent if performing it multiple times results in the same system state as performing it exactly once.

6. Why is idempotency critical for payments?
-> Idempotency is important in payments because it prevents an user from being double charged in case of any retries when the payment service gets timed out.

7. What is an idempotency key?
-> A unique identifier generated by the client that represents one logical operation, not one HTTP request. 
   The key says: No matter how many times I send this request, treat it as the same payment attempt.
   Example: Idempotency-Key: pay_8f3a9c2e

8. Can GET requests be non-idempotent?
-> GET endpoints are usually idempotent by nature, but GET requests are sometimes implemented in non-idempotent ways, for example:
    a. Tracking analytics counters (GET /page increments a view count)
    b. Triggering side effects (GET /resetPassword)
    c. Logging, auditing, or rate-limiting side effects.
    d. Cache-busting hacks that modify state
These violate HTTP semantics, but they do exist.

## Design Questions

9. How would you design idempotency for a high-throughput payment system?
-> To handle idempotency efficiently, I would store idempotency keys in Redis for fast lookup to handle retries without hitting the 
database repeatedly. However, Redis would only act as a cache. The database would remain the source of truth to ensure durability in 
case of Redis restarts or evictions. On every request, I’d first check Redis, fall back to the database if needed, and persist the 
final result in both. This gives us low latency without compromising correctness.

10. Where would you store idempotency keys and why?
-> In an in-memory cache such as Redis for faster look up of the already executed idempotent keys in case of retries. However, the primary
source of truth where all the idempotent keys will always be stored is the primary database. Idempotency is fundamentally about 
correctness under failure, not speed.

11. What happens if Redis restarts?
-> In case the Redis restarts or if the key is not found in the Redis cache, we will hit the primary database to fetch the key and then save the result in the cache once Redis is up.

12. How do you handle concurrent requests with the same idempotency key?
-> Exactly one request performs the side effect; all others observe the same outcome.

## Failure Scenarios

13. Payment succeeded but response timed out — what do you do?
-> In case of a payment timeout, I would not rollback a successful transaction because payments are external side effects. Instead, I would 
make the payment API idempotent using an idempotency key, persist the payment state reliably, and return an ambiguous response to the 
client. On retry, the same request would return the already processed result, preventing double charges while keeping the system consistent.

14. Client retries payment request — how do you prevent double charge?
-> By using idempotency keys that are generated by the payment service.

15. What happens if DB write succeeds but response fails?
-> If the database write succeeds but the response is never delivered, the operation must still be treated as successful because the database 
commit is the point of no return. From the client’s perspective the outcome is unknown, so it will retry the request, and idempotency ensures 
that retry does not repeat the side effect. When the server receives the retry with the same idempotency key, it looks up the existing record, 
sees that the operation already completed, and returns the previously stored result. This way, a lost response or server crash does not cause 
duplicate work or double charging, and the client eventually gets a consistent answer.

## Trade-offs

16. Why not rollback successful payments?
-> Because a payment gateway timeout does not mean the payment failed, and rolling back in that situation can easily make things worse, not safer.
rolling back on a timeout assumes knowledge you don’t have. The safer model is to accept uncertainty, make the charge operation idempotent, and 
resolve the final state through reconciliation rather than speculative rollback.

17. Why not rely only on Redis for idempotency?
-> Because Redis cannot give you correctness guarantees under failure, and idempotency in systems like payments is about correctness first, performance second.
Redis is an in-memory system with optional persistence, eviction, and TTLs. That means idempotency keys can disappear due to crashes, failovers, restarts, 
memory pressure, or configuration changes. If a key is lost, a retry that should have been deduplicated can be treated as a brand-new request, leading to 
duplicate side effects like double charges. In other words, Redis can forget—databases are designed not to.

18. How long should idempotency keys be retained?
-> There’s no single universal duration, but idempotency keys should be retained long enough to cover every realistic retry and reconciliation window for the operation. 
   The retention period is a correctness decision, not a storage one. 
    a. For synchronous API calls, the minimum is the maximum time a client might retry after an uncertain outcome—this includes client timeouts, mobile retries, 
       background job retries, and load-balancer retries. In practice, this is rarely minutes; it is usually hours. In payment systems, the window must also cover 
       asynchronous completion and reconciliation, such as delayed gateway responses or webhooks that arrive long after the initial request. Because of this, 
       most payment platforms retain idempotency keys for 24 to 72 hours, and often longer for high-value or high-risk operations.
    b. For webhook or event processing, retention is typically 7 to 30 days, because providers may retry events for days and clients may reprocess historical data. 
       The key rule is that an idempotency key must not expire while a retry is still possible; otherwise, an old retry can be mistaken for a new operation and 
       cause duplicate side effects.

## Advanced

19. How does idempotency differ from exactly-once processing?
-> Idempotency and exactly-once processing are related but solve different problems at different layers, and idempotency is the more realistic guarantee in distributed systems.
    a. Idempotency means that performing the same logical operation multiple times has the same effect as performing it once. The system assumes duplicates will happen—because of retries, 
       timeouts, crashes, or network issues—and is designed so those duplicates are harmless.
    b. Exactly-once processing, on the other hand, means that a message or event is processed one and only one time end to end. This is a delivery and execution 
       guarantee typically discussed in the context of messaging systems and stream processors. True exactly-once semantics are extremely hard to achieve across 
       system boundaries, because they require all participants (brokers, consumers, databases, and external APIs) to coordinate perfectly and atomically.

20. How would you scale idempotency handling to millions of requests per second?
-> To scale idempotency to millions of requests per second, you separate correctness from performance: a small, strongly consistent write path enforces “only once,” 
while everything else is optimized for speed. Idempotency keys are sharded by a stable hash so all requests for the same key hit the same partition, and contention is 
minimized because most keys are seen only once. The system uses an atomic “first writer wins” operation to claim a key, then performs the expensive work without holding locks. 
Caches are layered aggressively to serve repeat reads, but they are never authoritative—durable storage remains the source of truth. By keeping hot data small, avoiding global locks, 
and assuming retries are normal, idempotency scales linearly even at very high request rates.

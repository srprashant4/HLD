DAY-5: Cache Eviction, Hot Keys & Stampede Control

Day-5 Goals:
By the end of today, you should be able to:
    • Explain why caches fail even when designed correctly
    • Choose the right eviction strategy
    • Handle traffic spikes without melting the DB
    • Answer real interview failure scenarios


1) Cache Eviction – Why It Exists
   Cache is finite, data is infinite.
   When cache fills up, something must go.

   Two Core Questions:
       a) Which key to evict?
       b) When to evict?


2) Eviction Strategies

   a) LRU – Least Recently Used (Most Common)
      Idea:
          Evict data that hasn’t been used recently.

      Why it works:
          Recent access predicts future access.

      Problems:
          i) Fails during scan-heavy workloads. LRU works well for repeated access, but bulk one-time access can push out important data.
          ii) Hot keys can evict useful cold-but-important data

      Used in:
          • Redis
          • Memcached
          • CDN edge caches


   b) LFU – Least Frequently Used
      Idea:
          Evict keys used least often over time.

      Why it works:
          Protects truly hot data.

      Problems:
          i) Old popular data may stay forever
          ii) Needs an aging mechanism

      Used in:
          • Redis (approximate LFU)


   c) FIFO – First In First Out (Avoid in interviews)
      Idea:
          Evicts the oldest inserted entry.

      Problems:
          i) No awareness of usage
          ii) Poor performance


   d) TTL-based Eviction
      Idea:
          Keys expire automatically after a fixed time.

      Pros:
          i) Predictable memory usage
          ii) Prevents stale data

      Cons:
          i) Can cause cache stampede (we’ll fix this)


3) Cache Stampede (Very Important)

   Problem:
       Many requests hit cache at the same time for the same key.

   Scenario:
       i) Cache key expires
       ii) 10,000 requests arrive
       iii) All hit DB simultaneously

   Result:
       Database crashes.


4) Cache Stampede Solutions (Must Know)

   a) Solution 1: Locking (Single Flight)
      Flow:
          i) First request hits DB
          ii) Other requests wait

      Used in:
          • Redis Redlock
          • Application-level mutex


   b) Solution 2: Stale-While-Revalidate
      Flow:
          i) Serve stale data
          ii) Refresh cache in the background
          iii) Extremely popular in real systems


   c) Solution 3: TTL Jitter
      Idea:
          Randomize TTL slightly.

      Example:
          TTL = 10s ± random(0–2s)

      Benefit:
          Prevents synchronized expiration.


5) Hot Keys (Silent Killer)

   What is a Hot Key?
       A key accessed orders of magnitude more than others.

   Examples:
       • Homepage configuration
       • Feature flags
       • Popular product

   Why Hot Keys Are Dangerous:
       • Single Redis shard overloaded
       • Network bottleneck
       • Latency spikes


   Hot Key Mitigation Strategies:

       a) Key Sharding
          Example:
              user:123 → user:123:1, user:123:2

       b) Local In-Memory Cache (L1 + L2 Cache)
          i) JVM cache (Caffeine or Guava)
          ii) Redis as L2

       c) Replication
          • Read replicas for cache


6) Cache Penetration (Often Forgotten)

   Problem:
       Requests for non-existent keys.

   Explanation:
       Cache penetration happens when requests repeatedly ask for
       data that does not exist in the database and therefore also
       does not exist in the cache.

   Example:
       a) Requesting userId = 999999 repeatedly
       b) DB has no such user
       c) Cache miss every time
       d) DB hit every time

   Why Is This Dangerous?
       a) Cache provides no protection
       b) Database gets overloaded
       c) Often caused by bots or malicious traffic


   Solutions for Cache Penetration:

       a) Cache Null Values
          i) Cache the "not found" result with a short TTL
          ii) Prevent repeated DB hits

       b) Bloom Filters
          i) Probabilistic data structure
          ii) Quickly checks if a key may exist
          iii) Prevents unnecessary cache and DB lookups
          iv) If bloom filter says “impossible”, skip DB

       c) Relationship with Cache Stampede
          i) Cache penetration → invalid keys
          ii) Cache stampede → valid but expired keys
          iii) Both must be handled in production systems


7) Multi-Level Caching (L1 & L2 Cache)

   a) L1 Cache
      i) Closest cache to the application
      ii) In-memory within the same process (e.g., JVM cache)
      iii) Extremely fast (nanoseconds)
      iv) Limited size
      v) Lost on application restart
      vi) Examples:
          • Spring Boot with Caffeine
          • Guava Cache


   b) L2 Cache
      i) Shared, distributed cache
      ii) Network-based
      iii) Slightly slower than L1 but still fast
      iv) Survives application restarts
      v) Examples:
          • Redis
          • Memcached

      Typical Flow:
          Request → L1 Cache → L2 Cache → Database


   c) Why Use Multi-Level Cache?
      i) Reduce latency
      ii) Reduce network calls
      iii) Protect L2 cache from hot-key overload
      iv) Improve overall system resilience
